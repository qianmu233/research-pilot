# Phase 6：中文检索基准与证据质量验收

日期：2026-10-20。范围限定为当前模型与同一 PgVector 的中文检索诊断和证据完整性；没有接入真实 LLM、收费搜索、新数据库或多 Agent，也未修改 P1/P2/P3。

| 编码与归一化 | FastEmbed ONNX token 级输出取第一个 token（CLS），沿向量维度作 L2 归一化，epsilon=1e-12；384 维，本次查询范数 0.99999994–1.0 |
| 查询与文档 | `query_embed` / `passage_embed` 在此模型实现中最终调用同一 `embed`，没有自动 query/passage 前缀；相同中文输入实测向量一致 |

| PgVector | `vector(384)`，`<=>` 余弦距离，分数=1-distance，默认阈值 0.5；精确扫描。同分按 source_ref、chunk_id 稳定排序 |
| 分片 | 实际 tokenizer 的原文 offsets；默认 256 tokens、重叠 32，独立克隆 tokenizer 并取消分片器截断，推理 tokenizer 不变 |

| 去重 | SearchTools 与 merge_sources 按 locator + excerpt 去重；重复轮次保留原 S# 和元数据，不会把不同文档的同文片段合并成一个来源 |

实现依据来自本机已锁定的 FastEmbed 源码 `text_embedding_base.py`、`onnx_embedding.py`、`common/utils.py`，以及实际模型哈希和真实推理，不仅依赖文档自述。[ONNX 转换来源](https://huggingface.co/Qdrant/bge-small-en-v1.5-onnx-Q) 与原模型均保留在第三方声明中。

## 已证实的缺陷与最小修复

1. 原实现只使用缓存中的 main，记录过 commit 但不强制固定。现在显式下载该 revision，启动校验五个文件并通过 specific_model_path 加载；移动 main 或替换 tokenizer 不再静默生效。使用的实际权重、维度和编码没有变化。
2. PostgreSQL 已保存 source_ref/doc_id，但搜索与 API Evidence 模型丢掉这些字段。现在返回并保留元数据；词面降级路径也返回相应字段，旧证据通过可空默认字段兼容。没有改库表或迁移既有向量。
3. 返回的证据被硬截前 900 字符，虽已 token 切片仍会丢掉尾部。真实探针 1220 字符、未超单片 token 限额，原来只返回 900 字符且丢尾部标记；现在保留整个已存分片。

新增回归测试在修复前真实失败 2 项，XML 保留在基准目录；没有降低原断言。修复未换模型、未调整 0.5 阈值、未更改图拓扑或相关性标注。依赖版本不变。

## 固定基准与实际指标

19 篇明确标记的合成技术/干扰文档；20 道中文问题（16 有答案，4 无答案）。先冻结文档级标注与 SHA256，再执行真实模型 + PgVector；标注由开发助手编写，可人工检查但未独立复审。数据、每题金标/理由、逐题排序与指标定义见 [基准说明](../benchmarks/zh_retrieval_v1/README.md)。

| 指标（原实现与修复后相同） | 实际值 |
|---|---:|
| Recall@3（16 题宏平均） | 0.53125 |
| Recall@5（16 题宏平均） | 0.53125 |
| MRR@5（16 题） | 0.51041667 |
| 无答案零候选拒答率 | 0/4 = 0% |
| 多文档全部金标召回@5 | 0/4 |
| 全部 top-5 候选中不相关片段 | 90/100 |

最终所有返回来源都存在于真实数据库，去重和元数据检查为零错误；长证据探针尾部保留。相关性指标仍然较差，不能因程序测试通过就宣布质量通过。来源存在和完整返回，也不能证明该来源回答问题。

无答案 Q19 的真实 LangGraph 诊断仍以 completed 结束，并认为 5 个不相关来源“充分”。这是现有数量门槛的实质局限；没有将 Mock 流程完成当成可回答性，也没有把 Recall 当成报告准确率。

保留原有 24 项，新增 `tests/test_phase6_zh.py` 的 9 项：来源/数据库/Schema/去重关联、完整片段、冻结标签与手算指标、真实中文向量及范数、全基准完整性、模型缓存防篡改、空语料与相似超时概念、攻击文本及模型请求角色边界、真实 PgVector 断连后的工作流失败。

当前已执行全套 33 项通过；最终命令与 JUnit 位置以根目录 TEST_REPORT 为准。打包检查确认 wheel 中包含模型锁清单，避免源码环境通过而安装后找不到文件。没有新增依赖。

测试不为低 Recall 或误召回设置事后放宽的质量断言。模型输出均为固定预训练向量；请求角色测试仅用确定性 recorder 检查消息构造，不调用真实模型、不证明真实 LLM 能抵御所有注入。原图与 API、恢复测试均继续通过，图框架保持原样。

## 保留的失败与边界

- 英文 tokenizer 在本数据集 39 段文本中有 1682/2473 = 68.0146% `[UNK]`；同义改写与中文干扰分离表现差。不能仅凭这一现象断言所有排名错误的唯一成因。
- 0.5 分数阈值未识别任何无答案题；相似分数不是置信度。未使用此小集调阈值后再当独立验收。
- 多文档问题都未找齐来源，增加 top-k 或接入强 LLM不能自动补出缺失证据。
- 检索现在保留完整分片，但 Mock 仍展示每片前 220 字符；真实模型适配器仍有每片 600 字符、总证据约 9500 字符的既有预算。关键事实可能在上下文预算阶段被丢弃，本轮不把展示/预算截断称为已解决的报告质量。
- 文本里的 `[S999]` 等引用示例仍可能被 Mock 原样摘录并被保守引用校验拒绝；没有放宽不存在来源的拒绝规则。
- 只验证了数据未提升为 system 消息、Mock 未照攻击串改写任务、图未注册危险工具；未运行真实 LLM，不能声称完成通用 Prompt Injection 防御验收。
- 小型合成集没有独立人工盲评，未代表业务分布或生产性能。本轮未重建/部署 Docker，既有运行容器仍是 Phase 5 镜像；Phase 6 在当前工作区代码与专用数据库上验收。

## Phase 7 建议（仅方案，等待确认）

建议先确认免费本地、OpenAI-compatible 的中文模型端点及准确身份，再沿现有 ChatOpenAI 适配器接入，保留图和数据库。外部付费供应商仍需单独明确授权。本轮没有执行该步骤。

真实报告验收应事先标注可支持的事实、证据跨度与无答案要求，分别检查引用存在、事实支持、关键证据未被预算丢弃、无答案拒答；不能沿用“来源达到两条”作为语义充分性。模型不得用内部常识补造检索缺失的事实。

中文检索应另行批准在同一 PgVector 中对适合中文的模型与官方查询指令做隔离 collection 对照，并采用新盲测集；这会涉及维度/模型迁移方案，本轮未实施。当前英文基线及其失败必须保留。

**Phase 6 到此停止。Phase 7 的模型、端点、费用和质量验收方案等待用户确认。**
