# ResearchPilot 多智能体流程与面试指南

用企业 RAG 知识库选型来理解这条链路。团队已经导入 PgVector、Milvus 和 Elasticsearch 的内部试点纪要。这次要比较检索、部署、扩展和运维，保留引用，并标出试点材料回答不了的问题。

## 1. 用户输入

先用 `POST /api/documents/text` 把资料导入已配置的检索库，再向 `POST /api/tasks` 提交 `question`、`scope` 和 `mode: "multi"`。问题决定研究目标，范围提供研究维度和业务约束。省略 `mode` 时仍走原单 Agent 流程。

## 2. 创建任务

FastAPI 返回 HTTP 202 和主任务 ID，并通过进程内后台任务启动 Runtime。SQLite 保存任务、模式和模型请求账本。主任务 ID 同时用作 LangGraph 的 `thread_id`，第一次运行记录限额和时间起点。客户端轮询 `GET /api/tasks/{id}` 查看进度。

## 3. 动态拆分

Supervisor 用原问题和范围生成结构化计划。例如一个选型问题可能拆成三个候选任务，一份单文档可能只需要一个子任务。Pydantic 检查目标、范围、维度、约束和查询。对明确列举的候选产品标识及“维度”字段，程序保留原候选和维度，以候选名发起首查，集中比较留到汇总阶段。自然语言主题仍由 Supervisor 拆分。子任务 ID 由主任务 ID 和规范化的目标、范围、维度生成，同一次研究内恢复时沿用。

## 4. 并行研究

主图用 LangGraph `Send` 给每个任务派发独立 Worker 子图。PgVector Worker 可以在自己的局部状态中保存部署和运维资料，Milvus Worker 同时执行自己的查询。两者共享配置好的词面或向量资料库，各自保存查询游标、本轮来源和局部编号。

## 5. 局部证据评估

每个子图执行「检索 → 评估 → 必要时重新检索」。评估记录覆盖维度、引用来源和缺口。检索词、来源和轮次先写入子任务游标。评估失败后恢复可以直接读取已保存的检索结果。

## 6. 汇总证据

主图在同一批 Worker 返回后汇总结果。Reducer 以子任务 ID 为键，较新的补查代数或重试尝试覆盖旧结果。汇总按计划顺序轮流取各子任务的来源，优先保留 Worker 已引用的证据，用 locator 和原文摘录去重，然后分配报告自己的 `S1`、`S2` 等编号。Worker 内的 `S1` 是局部编号。

## 7. 全局评估与定向补查

Review 对照原任务检查维度覆盖、证据缺口和资料冲突。比如 Review 要求补查，而 PgVector 当前摘录没有写“运维”，系统用“PgVector 运维”收敛检索。关键词是否出现只影响查询选择。Supervisor 检查子任务 ID、历史查询、轮次和剩余时间后再分发。当前每个主任务最多一批全局补查。补查未获得新证据时复用已有局部评估，保留全局复核和报告的额度。

## 8. 生成报告

写入节点接收合并证据和 Review 的结构化结果。Ollama 报告先选具体原文段落的编号，再填写该段支持的发现。程序把模型选择映射回对应来源 ID 和原文，公开报告字段保持兼容。达到调用、时间或上下文边界时，报告明确标出局限，候选摘录仍可在任务结果中查询。`status=completed` 说明有报告可读，`progress.quality` 说明当前结果是 `full`、`partial` 还是 `insufficient`。

## 9. 引用校验

程序检验引用 ID 是否来自本轮全局证据、摘录是否是对应来源的原文子串，以及报告是否夸大了 Review 给出的充分性。未知 ID、错误摘录或不受支持的 `answered` 会阻止发布，报告接口返回 409。结论的事实性和资料可靠性仍需人工复核。

## 10. 结果保存与查询

Runtime 将状态、报告及来源写入任务记录。客户端通过 `GET /api/tasks/{id}` 查看阶段、证据、子任务和调用次数，通过 `/report` 读取已发布报告，通过 `/trace` 复盘节点、补查和模型调用。报告状态与质量分开读取，已完成任务仍可能只有部分报告。

## 恢复任务

运行失败或硬退出后，用原任务 ID 请求 `POST /api/tasks/{id}/resume`。主图从 SQLite Checkpointer 继续，子图读取任务库中已保存的检索或评估游标。若 PgVector 和 Milvus 已经完成，而 Elasticsearch 在评估时遇到接口错误，恢复时只尝试 Elasticsearch 的待执行评估，已保存的检索结果继续使用。同一批分发失败后允许一次手动重试，仍失败则可输出披露缺口的部分报告。恢复沿用原调用账本和绝对时限。进程在外部调用返回和本地持久化之间退出时，该阶段可能重放并再次预占额度。

## 面试时用三条线讲清楚

| 线索 | 讲法 |
|---|---|
| 数据流 | `question` 与 `scope` → 结构化子任务 → 局部来源与结论 → 全局来源 → 报告引用 |
| 控制流 | Runtime 选择模式，Supervisor 用 `Send` 动态派发，汇总后由 Review 决定补查或写作 |
| 状态流 | `task_id = thread_id` 定位主图，`task_id + subtask_id` 定位 Worker 游标，全局预算账本记录每次模型尝试 |

## 常见追问与参考回答

**单 Agent、普通 Workflow、固定并行和 Multi-Agent 怎么区分？**

| 形态 | 分工与决策 |
|---|---|
| 普通 Workflow | 流程节点和路由规则由代码预先定义。节点可以调用模型或做条件判断 |
| 本项目单 Agent | 一个研究上下文执行计划、检索、评估、写作和校验。评估可提出补查查询 |
| 固定并行 | 预先指定任务与搜索范围，各分支并行，之后统一汇总。实验中的 B 组关闭补查 |
| 本项目 Multi-Agent | Supervisor 按输入决定子任务，Worker 独立维护证据与局部决策，全局 Review 根据缺口发起定向补查。LangGraph 仍负责节点、路由和约束 |

**怎么证明是真并行，预算如何防止并发超扣？** 主图通过 `Send` 分发 Worker 输入，集成测试验证派发的运行区间重叠。所有请求共用 SQLite 账本，调用前在 `BEGIN IMMEDIATE` 事务中读取并增加用量。上限、写作预留和总时限在预占时检查。Ollama 单路配置仍可能让推理请求排队。

**进程在关键时刻崩溃怎么办？** SQLite 中已有主图检查点和 Worker 游标。已保存的检索或已完成的子任务可复用。外部调用返回与本地落盘之间发生崩溃时，该阶段可能重放并继续扣原预算。进程内活跃任务集用于防止同一任务重复启动。

**为什么来源和摘录都匹配，结论仍可能有问题？** 摘录来自本轮资料库，但模型可能增加原文没有的推论。真实 RAG 复查中 7 条引用全部匹配，人工严格核对只有 1 条结论完整相关且获证。两类指标分别记录。

**Multi-Agent 何时值得用？** 单文档或目标明确时用默认单 Agent。候选多、可分工且需按缺口补查时考虑 Multi-Agent。真实 A/B/C 的一次可比运行中，动态组和固定组各找到 3/4 关键材料，动态组耗时更高。最终复查额外找到一份资料，样本仍不足以推断普遍优势。

建议按 `api.py` → `runtime.py` → `multi_workflow.py` → `research_agent.py` → `store.py` 和引用校验的顺序读源码，然后用 `tests/test_multi_agent.py` 对照边界条件。
