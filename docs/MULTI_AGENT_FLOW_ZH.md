# ResearchPilot 多智能体执行流程

本文说明多 Agent 模式的控制流、证据流和持久化方式。HTTP 接入与示例见[项目主页](../README.md)，运行结果见[多智能体验收记录](MULTI_AGENT_ACCEPTANCE_ZH.md)。

## 1. 用户输入

使用 `POST /api/documents/text` 将资料导入已配置的检索库，再向 `POST /api/tasks` 提交 `question`、`scope` 和 `mode: "multi"`。问题决定研究目标，范围提供研究维度和业务约束。省略 `mode` 时使用默认的单 Agent 流程。

## 2. 创建任务

FastAPI 返回 HTTP 202 和主任务 ID，并通过进程内后台任务启动 Runtime。SQLite 保存任务、模式和模型请求账本。主任务 ID 同时用作 LangGraph 的 `thread_id`，第一次运行记录限额和时间起点。客户端轮询 `GET /api/tasks/{id}` 查看进度。

## 3. 动态拆分

Supervisor 用原问题和范围生成结构化计划。例如一个选型问题可能拆成三个候选任务，一份单文档可能只需要一个子任务。Pydantic 检查目标、范围、维度、约束和查询。对明确列举的候选产品标识及“维度”字段，程序保留原候选和维度，以候选名发起首查，集中比较留到汇总阶段。自然语言主题仍由 Supervisor 拆分。子任务 ID 由主任务 ID 和规范化的目标、范围、维度生成，同一次研究内恢复时沿用。

## 4. 并行研究

主图通过 LangGraph `Send` 按子任务分发独立的 Worker 子图。PgVector Worker 可以在自己的局部状态中保存部署和运维资料，Milvus Worker 同时执行自己的查询。两者共享配置好的词面或向量资料库，各自保存查询游标、本轮来源和局部编号。

## 5. 局部证据评估

每个子图执行「检索 → 评估 → 必要时重新检索」。评估记录覆盖维度、引用来源和缺口。检索词、来源和轮次先写入子任务游标。评估失败后恢复可以直接读取已保存的检索结果。

## 6. 汇总证据

主图在同一批 Worker 返回后汇总结果。Reducer 以子任务 ID 为键，较新的补查代数或重试尝试覆盖旧结果。汇总按计划顺序轮流取各子任务的来源，优先保留 Worker 已引用的证据，用 locator 和原文摘录去重，然后分配报告自己的 `S1`、`S2` 等编号。Worker 内的 `S1` 仅在该子任务内有效。

## 7. 全局评估与定向补查

Review 对照原任务检查维度覆盖、证据缺口和资料冲突。例如，若 PgVector 的现有摘录缺少“运维”维度的证据，系统可用“PgVector 运维”缩小检索范围。关键词匹配用于调整查询。Supervisor 检查子任务 ID、历史查询、轮次和剩余时间后再分发。当前每个主任务最多一批全局补查。补查未获得新证据时复用已有局部评估，保留全局复核和报告的额度。

## 8. 生成报告

报告生成节点接收合并证据和 Review 的结构化结果。Ollama 报告先选具体原文段落的编号，再填写该段支持的发现。程序把模型选择映射回对应来源 ID 和原文，公开报告字段保持兼容。达到调用、时间或上下文边界时，报告明确标出局限，候选摘录仍可在任务结果中查询。`status=completed` 说明有报告可读，`progress.quality` 说明当前结果是 `full`、`partial` 还是 `insufficient`。

## 9. 引用校验

程序检验引用 ID 是否来自本轮全局证据、摘录是否是对应来源的原文子串，以及报告是否夸大了 Review 给出的充分性。未知 ID、错误摘录或不受支持的 `answered` 会阻止发布，报告接口返回 409。结论的事实性和资料可靠性仍需人工复核。

## 10. 结果保存与查询

Runtime 将状态、报告及来源写入任务记录。客户端通过 `GET /api/tasks/{id}` 查看阶段、证据、子任务和调用次数，通过 `/report` 读取已发布报告，通过 `/trace` 追踪执行节点、定向补查和模型调用。报告状态与质量分开读取，已完成任务仍可能只有部分报告。

## 恢复任务

运行失败或硬退出后，用原任务 ID 请求 `POST /api/tasks/{id}/resume`。主图从 SQLite Checkpointer 继续，子图读取任务库中已保存的检索或评估游标。若 PgVector 和 Milvus 已经完成，而 Elasticsearch 在评估时遇到接口错误，恢复时只尝试 Elasticsearch 的待执行评估，已保存的检索结果继续使用。同一批分发失败后允许一次手动重试，再次失败时可生成注明缺口的部分报告。恢复沿用原调用账本和绝对时限。若进程在外部调用返回后、结果持久化前退出，恢复时可能重新执行该阶段并再次占用原额度。

## 状态与持久化

| 层级 | 保存内容与用途 |
|---|---|
| 主图检查点 | 通过任务 ID 定位图线程，保存计划、已合并结果及下一步，恢复后继续协调研究 |
| 子任务游标 | 通过任务 ID 与子任务 ID 保存各 Worker 的检索、评估和补查进度，恢复时复用已经落盘的步骤 |
| 主任务与模型账本 | SQLite 保留任务状态、引用、轨迹及模型调用记录，供 API 查询和预算计算 |

模型调用前，任务库通过 SQLite 的 `BEGIN IMMEDIATE` 在同一事务中核对并预占共享额度。Worker 同时受并发、检索轮次、单步超时和主任务总时限约束。失败或超时仍计入调用次数。主图为全局评估和报告生成预留额度。
